# Dogear 折角 · Windows 剪切板工具（可行性分析与设计报告 v2）

- 技术方案：Tauri 2 + Vue 3 + TypeScript + SQLite
- 目标平台：Windows 10 / 11（x64），交付形式为 exe（安装包 + 可选便携版）
- 产品形态：先免费；本地优先、默认不联网
- 差异化功能（本版新增）：① 开发者友好（自动识别 JSON / URL / 颜色值 / SQL / 代码，一键格式化与预览）　② 图片文字提取 OCR（复制截图后直接取出文字）
- 文档用途：项目立项说明，可直接作为 Cursor 的项目上下文（见第 17 节）

> **阅读须知（请先看）**
> 1. 文中涉及的插件、Windows 接口、crate 名称是我基于对 Tauri 2 与 Windows 开发的了解给出的**推荐方案**，开工前必须对照官方文档核对当前版本的 API，特别是：Tauri 窗口特效、`Windows.Media.Ocr`、`windows` crate 的 feature 名称。凡标注「需核对」「需实测」的地方均为我不确定的点。
> 2. 第 7 节的竞品概述以常识为主，**不是实时调研**；其中少量内容来自名称查重时的几次网络搜索摘要，也未逐一深入核实。
> 3. 工作量、体积、性能数字都是经验估算，不是实测数据。

## 第一部分：可行性分析

### 1. 结论

**可行，风险中等，建议立项。** v1 的核心能力（监听剪切板、全局快捷键、托盘、开机自启、本地数据库、打包 exe）在 Tauri 2 里都有官方或成熟社区插件，风险点仍是自动粘贴与剪切板监听稳定性。

v2 新增的三块能力评估如下：

- **识别与格式化**：纯逻辑，没有系统依赖，可行性高；风险在于启发式识别的误判，通过严格规则、可手动更正、可关闭来控制。
- **OCR**：Windows 自带 OCR 接口 `Windows.Media.Ocr`（离线）可直接从 Rust 调用，可行性中高；风险在于依赖系统语言包、中文识别效果与排版还原需要实测。有备选方案（第 10.2 节）。
- **毛玻璃 / 半透明**：Tauri 2 自带窗口特效能力（Mica / Acrylic 等，需核对），Win11 效果好，Win10 需降级，可行性中高；风险在于 Acrylic 在个别系统版本上拖动、缩放时的性能问题（需实测）。

另外，市场上同类工具已不少，**部分已经带 OCR**（见第 7 节）。所以产品的成败更取决于「组合体验 + 中文场景 + 颜值打磨 + 免费无打扰」，而不是单个功能点。这是本版最重要的判断，请据此安排精力：UI 打磨与稳定性的优先级不低于新功能。

### 2. 技术可行性逐项评估

v1 已有的条目保持不变（读写文本、监听变化、全局快捷键、托盘、自启、SQLite、单实例、窗口记忆、自动粘贴、无边框窗口、打包），此处仅列新增与有变化的条目。

| 能力 | 实现方式 | 可行性 | 备注 |
|---|---|---|---|
| 读取图片 | Rust 侧读取位图，转 PNG 落盘，库里只存路径、缩略图与尺寸 | 中高 | 提前到第一批功能，因为 OCR 依赖它 |
| 截图取字（OCR） | Rust 通过 `windows` crate 调用 `Windows.Media.Ocr`，离线识别 | 中高 | 依赖系统已安装的 OCR 语言包；详见 10.2，需核对 API |
| OCR 备选 | Tesseract 或 PaddleOCR（ONNX）随包携带 | 中 | 体积与集成成本更高，仅作降级或增强 |
| 内容类型识别 | Rust 侧在入库时做轻量规则识别（JSON / URL / 颜色 / SQL / 代码） | 高 | 规则见 10.1，需严格控制误判与耗时 |
| 格式化 | JSON 用 Rust 的 `serde_json`；SQL 用前端 `sql-formatter`（需核对）；代码高亮与格式化懒加载 | 高 | 大体积库（如 Prettier）只在用户点击时动态加载 |
| 搜索图片中的文字 | OCR 结果存入数据库，参与搜索 | 高 | 数据量大时用 SQLite FTS5 |
| 毛玻璃 / 半透明窗口 | Tauri 2 窗口特效（Mica / Acrylic / Blur，底层依赖 window-vibrancy 一类能力，需核对）+ 透明 WebView | 中高 | Win11 好；Win10 降级；见 12.5 |
| 浅色 / 深色主题自动跟随 | 前端读系统主题（`prefers-color-scheme`）+ Tauri 主题事件 | 高 | 需核对事件名 |
| 图标与安装包品牌化 | 用 `tauri icon` 命令由 1024 PNG 生成各尺寸（需核对） | 高 | 素材已提供 |

### 3. 开发者能力匹配度

- 前端（Vue 3）约占 60% 到 65%：v2 增加了预览面板、识别徽标、格式化视图、主题与动效，前端占比略升。
- Rust 约占 35% 到 40%：监听、粘贴、SQLite、识别规则、OCR 调用。OCR 部分是新增的 Rust 内容，其中涉及 Windows 异步接口，建议先做独立小原型（M0b）。
- 建议边界不变：Vue 只通过 `invoke` 与事件和 Rust 通信；识别规则与 OCR 都放在 Rust 侧，保证呼出面板时不卡顿。

### 4. 环境与成本

- 开发环境：Node.js、Rust 工具链、MSVC 生成工具、WebView2；**OCR 与毛玻璃都必须在真实 Windows 上验证**，不能只靠虚拟机截图或 Linux 环境。建议准备 Win10 与 Win11 各一台（或虚拟机）测降级。
- 费用：开发阶段为 0；因为免费发布，代码签名证书仍是可选项，但不签名会遇到 SmartScreen 提示与杀软误报（R4），建议至少在发布页写清说明。
- 体积预期：如果只用 Windows 自带 OCR，安装包体积基本不增加；如果携带 Tesseract 或 ONNX 模型，会增加数 MB 到数十 MB（需核对具体模型）。
- 常驻资源：OCR 只在有新图片时运行，识别完即释放；空闲时不应占 CPU。以上均为预期，需实测。

### 5. 风险与对策

R1 到 R8 同 v1（自动粘贴、监听稳定、敏感内容、杀软误报、快捷键冲突、大内容、WebView2 缺失、管理员窗口），此处略去，下表仅列新增风险。

| 编号 | 风险 | 影响 | 对策 |
|---|---|---|---|
| R9 | 系统缺少 OCR 语言包（尤其中文） | 中文识别不可用或结果很差 | 启动与首次 OCR 时检测可用语言；提示并引导到系统语言设置；允许指定识别语言；必要时启用备选引擎 |
| R10 | OCR 中文效果不如预期（字间空格、标点、排版、小字、深色截图） | 体验不及预期 | M0b 用同一批样例实测并与备选方案对比；做后处理（去 CJK 间多余空格）；结果区允许直接编辑；保留「重新识别」 |
| R11 | OCR 占用 CPU 或阻塞界面 | 卡顿、发热 | 串行队列、后台线程、超时与取消；大图先缩放；可设置「仅手动识别」 |
| R12 | 内容类型误判（把普通文本当 JSON/代码，把 `#123` 当颜色） | 干扰用户 | 严格规则（整段内容匹配才触发）；识别徽标可手动更正；设置里可关闭智能识别；不改写原始内容，格式化只作用于预览与「粘贴格式化」 |
| R13 | 毛玻璃在 Win10 或部分显卡上效果差、拖动卡 | 观感与性能下降 | 12.5 的降级阶梯：Acrylic → Blur → 半透明纯色 → 纯色；检测系统「透明效果」开关；设置里提供「减少透明效果」 |
| R14 | 同质化竞品多 | 增长困难 | 聚焦中文场景与开发者场景的组合，打磨细节；持续观察竞品（第 7 节） |
| R15 | 名称、图标与商标冲突 | 无法上架或被投诉 | 发布前做正式商标检索（第 8.3 节）；先在小范围发布 |
| R16 | 字体、图标版权 | 法律风险 | 不打包 SF Pro 等无再分发许可的字体；用系统字体；图标自绘或使用宽松许可图标库（如 Lucide，需核对许可） |
| R17 | 识别结果或 OCR 文本中含敏感信息 | 隐私风险 | OCR 文本与原图同等对待：遵守黑名单、可一键清除、不联网、日志不记录内容 |

### 6. 原型验证清单（建议先花 3 到 4 天完成）

在 v1 的 5 项基础上，增加 OCR 与毛玻璃两个独立小原型。按风险从高到低：

1. 监听文本剪切板变化，并在 Vue 界面实时显示。
2. Alt+V 呼出无边框窗口，Esc 或点击外部可关闭。
3. 在记事本、浏览器、VS Code 中选中一条记录按回车，能自动粘贴到原位置。
4. 复制来自密码管理器的内容时，能识别并跳过。
5. 打包出 exe，在干净的 Windows 虚拟机里安装并运行。
6. **（M0b）OCR 小原型**：写一个独立的 Rust 小程序或命令，读取一张 PNG，调用 `Windows.Media.Ocr` 输出文字。验收：
   - 用 20 张样例图（中文文档、英文、微信聊天、代码截图、表格、深色模式、小字、低分辨率各若干）实测，记录耗时与人工抽查的准确程度；
   - 验证在**没有中文语言包**的机器上的行为与错误信息；
   - 验证中文输出是否出现字间空格；
   - 如果效果明显不够，同样的样例用 Tesseract 或 PaddleOCR 对比，再决定是否改方案。
7. **（M0c）毛玻璃小原型**：透明无边框窗口 + Mica / Acrylic，在 Win11 与 Win10 各看一眼效果，并拖动窗口观察是否卡顿；验证「系统关闭透明效果」时的表现。

## 第二部分：产品与设计报告

### 7. 市场与用户画像

> 声明：本节为基于常识的概述，不是实时市场调研，不含销量、用户量或排名数据。竞品功能随版本变化很快，描述可能过时，立项前请自行复核。

#### 7.1 市场概述

- **需求本身是刚需但已被「基础满足」**：Windows 10/11 自带剪切板历史（Win+V），据我了解有条数限制、搜索与管理能力较弱、重启后非固定项会被清除（需核对当前系统行为）。这让「完全没有历史」的用户很少，竞争点变成「更好用、更好看、更多智能」。
- **工具类产品的同质化很高**：几乎所有同类工具都有历史、搜索、置顶、快捷键。因此用户感知差异主要来自：呼出速度与稳定性、界面质感、对特定人群的智能处理。
- **本机 OCR、开发者辅助已有人在做**：名称查重时的搜索摘要里，出现了若干带 OCR 的 Windows 剪切板类工具（见 7.2 备注）。因此「有 OCR」本身不能算壁垒，要靠体验打磨（自动、不打断、搜索得到、中文效果好）。
- **免费策略**：先免费有利于早期传播；但要提前想好不依赖账号体系和云服务，以免未来变现时迁移成本高。本版不设计任何收费或账号逻辑。

#### 7.2 竞品概述（常识性，不构成评测）

| 类型 | 代表产品（举例） | 常见特点 | 对本产品的启发 |
|---|---|---|---|
| 系统自带 | Windows 剪切板历史（Win+V） | 零安装、体验统一；功能简单 | 本产品要在「快、准、全」上明显优于它，否则用户没有迁移理由 |
| 老牌开源 | Ditto、CopyQ、Clipjump | 功能全、可定制；界面偏传统、上手门槛高 | 界面质感与新手友好是机会 |
| Windows 新秀（近年） | Cliptoo、Klip、Cubby Clipboard、PasteBar、QuickClipboard、TieZ、PasteIt、贴贴（TIETie）、快贴等 | 很多采用 Fluent / Mica 风格；部分带 OCR、截图、同步或 AI 功能 | 说明方向可行也说明竞争已存在；需做「组合 + 打磨」 |
| macOS 参照 | Paste、Maccy、Raycast 剪贴板历史等 | 设计质感高、键盘驱动、预览细腻 | 视觉与交互的参照对象（只参考风格，不抄袭具体设计） |
| 云同步类 | 快贴等 | 跨设备同步 | 本产品暂不做，保持「本地优先」 |

备注：上表第三行中的产品名来自我在 2026-10-02 为名称查重所做的几次网络搜索摘要（含 GitHub 仓库页与官网摘要），**我没有逐个安装或核实其功能与现状**，仅用于判断「赛道有人」。

#### 7.3 用户群与使用场景

| 用户群 | 典型场景 | 最在意 | 本产品对应功能 | 优先级 |
|---|---|---|---|---|
| 办公（行政、运营、财务） | 在表格、邮件、IM 间来回复制数字与话术；从微信、PDF 截图里取文字 | 快、不丢、能搜到 | 历史与搜索、置顶收藏、OCR 取字、数字键快速粘贴 | 高 |
| 学生 | 摘抄网页与文献；把课件、截图中的文字取出来；整理笔记 | 简单免费、取字准 | OCR、搜索（含图片内文字）、链接整理 | 高 |
| 设计 | 复制颜色值、图片素材、文案；在多个软件间传图 | 好看、颜色可视 | 颜色块预览与格式转换（HEX / RGB / HSL）、图片历史、界面质感 | 中高 |
| 开发 | 复制接口返回、SQL、日志、URL、代码片段 | 识别、格式化、不打断 | JSON / SQL / 代码识别与格式化、URL 处理、纯文本粘贴 | 高（差异化核心） |
| 客服 / 销售 | 反复粘贴固定话术、订单号、地址 | 极快、可固定、可编号 | 置顶收藏、1 到 9 数字键粘贴、搜索；后续的片段模板（P2） | 中高 |
| 注重隐私的用户 | 不希望剪切板内容上云 | 可信 | 本地存储、不联网、敏感内容跳过、黑名单、一键清空 | 中（所有人的底线） |

跨人群的共同需求：**快**（呼出到可输入的时间）、**稳**（不丢记录、不粘错窗口）、**好看**（愿意常驻）。这三点优先于任何单点功能。

关于「覆盖尽可能广」的取舍：

- 默认界面保持简约，不堆开发者术语；智能识别以「徽标 + 预览」的方式出现，普通用户不会被打扰，开发者能感到被理解。
- 提供中文界面为主、英文界面为辅（`vue-i18n`，V1.0 前完成，需核对）。
- 无障碍与可读性：键盘全程可用；对比度见 12.2；支持 125% / 150% 缩放；支持系统高对比度模式（降级为纯色，见 12.5）。

#### 7.4 小结：差异化判断

1. 单点功能（OCR、格式化）不是壁垒，**「复制即识别、选中即预览、回车即用」的连贯体验**才是。
2. 开发者与大众用户可以共存：识别做成「增强而不打扰」，且可关闭。
3. 视觉质感是低成本、可感知的差异点，但必须以性能与稳定为前提（毛玻璃不能拖慢呼出速度）。
4. 以上均为判断，缺乏用户调研数据。建议 M3 之后找 5 到 10 位不同身份的人试用，收集反馈，再决定 P2 的取舍。

### 8. 产品定位与品牌

#### 8.1 定位

**一句话定位**：一个轻量、离线、好看的 Windows 剪切板——复制过的都找得回，复制的东西自动认得出：JSON 一键格式化、颜色即时预览、截图直接取字。

**核心价值**：
1. 快：快捷键呼出，输入即搜索，回车即粘贴。
2. 懂：自动识别 JSON / URL / 颜色 / SQL / 代码；截图自动取字。
3. 美：简约、留白、圆角、毛玻璃，有苹果产品的质感，但遵守 Windows 习惯。
4. 私：数据只在本机，不联网，OCR 也在本机完成。
5. 免：先免费，无广告，无账号。

**非目标（当前版本不做）**：云同步、移动端、团队共享、云端 AI / 云端 OCR、账号体系、收费功能。

#### 8.2 候选名称（3 个）

查重方法：用 WebSearch 做了「名称 + clipboard / 剪贴板」的简单搜索，只能说明「前几页结果里有没有明显同名剪切板软件」，**不是商标检索，也不能保证没有重名**。

| 候选 | 含义 | 简单查重结果（2026-10-02） | 图标联想 | 风险 |
|---|---|---|---|---|
| **Dogear · 折角**（推荐） | Dog-ear 指书页折角，用来标记「这页值得回头看」，对应「把复制过的留住、随时回来」；折角也是「文档」的通用图形 | 搜索未发现同名 Windows 剪切板产品；搜到一个名为 DogEar 的 GitHub 项目，用途我未核实 | 一张带折角的纸，最简洁、最易识别 | 英文是常见词，商标可注册性与可检索性需确认；「折角」中文有其他含义，搜索结果可能较杂 |

### 10. 差异化功能详细设计

#### 10.1 开发者友好：识别与格式化

**总体原则**：
1. **只增强，不改写**：原始内容永远原样保存；格式化结果只用于预览与「粘贴格式化」动作（用户明确选择才粘贴）。
2. **宁缺毋滥**：要求整段内容（去首尾空白）匹配规则才识别，避免把普通句子识别成代码。
3. **便宜优先**：按成本由低到高依次尝试；设置字节上限（初始值：识别只处理前 100 KB，超过则跳过，需实测调整）；总耗时目标小于 5 ms（目标值，需实测）。
4. **可更正、可关闭**：预览区徽标点击可改类型；设置里可整体或逐类关闭。
5. **识别在入库时进行**（Rust 侧），结果写入 `subtype` 与 `meta` 字段，呼出面板时不再计算。

**识别顺序与规则**（命中即停）：

| 顺序 | 类型 | 判定规则（初版） | 误判控制 | 预览与一键动作 |
|---|---|---|---|---|
| 1 | 颜色值 | 整段（≤ 40 字符）匹配：`#RGB`、`#RGBA`、`#RRGGBB`、`#RRGGBBAA`；`rgb()` / `rgba()`；`hsl()` / `hsla()`（参数范围合法） | 必须整段只含颜色；`#123456` 这类可能是编号的内容仍会被识别为颜色——因此类型徽标可更正 | 色块 + HEX / RGB / HSL 三种格式，每种一键复制；按钮「粘贴为 HEX / RGB / HSL」 |
| 2 | URL | 整段无空白，以 `http://`、`https://` 开头，或 `www.` 开头且能解析出域名 | 多行或含空白的不算；`file://` 默认不识别 | 域名高亮；动作：在浏览器打开（需用户点击）、复制净化后的链接（去掉 `utm_*`、`fbclid` 等常见追踪参数，参数名单需维护）；**不联网抓取标题**，保持离线 |
| 3 | JSON | 去首尾空白后首字符为 `{` 或 `[`，且 `serde_json` 解析成功；解析失败但「很像 JSON」（含尾逗号、单引号、注释）则标为「疑似 JSON」并提供「宽松修复」 | 纯数字、纯字符串、单个 `[1]` 这类过短内容不识别（至少含一个键值对或 ≥ 2 个元素的数组，需调整）；使用 `preserve_order` 保持键顺序；大整数注意精度（`arbitrary_precision`，需核对） | 格式化（缩进 2 空格）/ 压缩 / 原文三视图；语法高亮；显示行数、深度、字节数、压缩后字节数；动作：复制格式化结果、粘贴格式化 |
| 4 | SQL | 首个单词（忽略注释与空白、不区分大小写）为 `SELECT / INSERT / UPDATE / DELETE / WITH / CREATE / ALTER / DROP`，且同时含对应关键字（`FROM / INTO / SET / TABLE / VALUES` 等） | 需同时满足「起始关键字 + 配套关键字」；单个单词 `select` 不识别 | 关键字高亮；格式化（前端 `sql-formatter`，需核对；支持选择方言：MySQL / PostgreSQL / SQLite / 通用）；动作：粘贴格式化、压缩为单行 |
| 5 | 代码 | 打分制：多行；含 `{ } ( ) ; =>`、`import / export / function / def / class / const / let / var / return / <div` 等特征；缩进规律；注释符号；达到阈值才识别 | 阈值偏保守；含大量中文句子的文本降分；同样可更正 | 语言猜测（初版仅区分 JS/TS、Python、Shell、HTML/XML、CSS、Rust、Go、Java、其他）；语法高亮（前端懒加载高亮库，如 highlight.js 或 shiki，需评估体积与离线可用）；格式化放 P2 |
| 6 | 普通文本 | 其余 | — | 纯文本预览 |

**数据存储**：`clips.subtype`（`json / url / color / sql / code:ts / ...`），`clips.meta`（JSON 字符串，如颜色的解析结果、JSON 的行数与深度、URL 的域名）。

**搜索联动**：支持前缀过滤 `type:json`、`type:color`、`type:sql`、`ocr:关键词`（只搜 OCR 文本）。

**交互**：
- 列表项：类型图标 + 徽标（JSON / SQL / TS 等）；颜色项左侧直接显示色块。
- 右侧预览区：顶部显示「已识别」状态与类型；中部为预览；底部为一键动作。
- 快捷键：`Ctrl+F` 在预览中切换格式化 / 原文；回车粘贴当前视图对应的内容（默认粘贴原文，格式化视图下回车即「粘贴格式化」——此行为需要可在设置里配置，避免用户误粘贴被改写的内容）。

#### 10.2 图片文字提取（OCR）

**目标体验**：用户用 Win+Shift+S（系统截图）或任何方式复制了一张图 → 列表里出现该图片项并显示「正在识别文字」→ 几秒内变为「已提取 N 字」→ 选中后右侧显示图片与识别文字 → 一键复制文字，或 Shift+回车直接粘贴文字。整个过程不弹窗、不打断。

**方案评估**

| 维度 | 方案 A：Windows.Media.Ocr（推荐首选） | 方案 B：Tesseract | 方案 C：PaddleOCR + ONNX Runtime | 方案 D：云端 OCR |
|---|---|---|---|---|
| 是否离线 | 是（系统组件） | 是 | 是 | 否，**违背「默认不联网」，不采用** |
| 额外体积 | 几乎为零 | 引擎与语言数据随包，约数 MB 到十几 MB（需核对） | 模型与运行时随包，约十几 MB 到数十 MB（需核对） | 无 |
| 中文支持 | 支持（依赖系统已安装的中文 OCR 语言包） | 支持（需携带 chi_sim 数据，效果与排版相关） | 通常对中文更友好（经验判断，未实测） | — |
| 集成难度 | 中：Rust 通过 `windows` crate 调用 WinRT 异步接口 | 中高：C++ 依赖、打包与线程 | 中高：模型加载、预处理与后处理要自己写 | 低，但不采用 |
| 授权 | 系统接口 | 开源许可（Apache-2.0，需核对） | 开源许可（模型与代码许可需分别核对） | — |
| 主要风险 | 用户缺语言包；中文字间空格；排版还原一般 | 体积大；中文复杂排版效果不稳 | 工程量与体积 | 隐私 |
| 角色 | **首选** | 降级备选 | 增强备选（可选下载，联网需用户同意） | 不采用 |

表中「效果」类结论属经验判断，**必须在 M0b 用同一批样例实测对比后才能定案**。

**首选方案：`Windows.Media.Ocr`（需让开发时核对 API）**

据我了解，相关要点如下（均需对照微软官方文档确认）：
- 命名空间 `Windows.Media.Ocr`，核心类型 `OcrEngine`、`OcrResult`（含 `Lines`、`Words`、`Text`）。
- 创建引擎：`OcrEngine::TryCreateFromUserProfileLanguages()`（按用户系统语言列表）或 `OcrEngine::TryCreateFromLanguage(Language)`（指定语言）；`OcrEngine::IsLanguageSupported(...)` 与 `OcrEngine::AvailableRecognizerLanguages()` 用于检测可用语言。
- 识别：`engine.RecognizeAsync(SoftwareBitmap)`，输入为 `SoftwareBitmap`；`OcrEngine::MaxImageDimension` 给出支持的最大边长，超过则需先缩放。
- 语言包：识别语言取决于系统已安装的 OCR 语言能力（在 Windows 设置的「语言和区域」中安装对应语言包，通常包含 OCR 组件；具体入口与能力名称需核对）。无对应语言包则 `TryCreate...` 可能返回空。
- 从 Rust 调用：使用 `windows` crate（需核对 crate 版本与需要启用的 feature，通常涉及 `Media_Ocr`、`Graphics_Imaging`、`Globalization`、`Storage_Streams`、`Foundation`）。

示意代码（**仅示意流程，不保证可直接编译，必须按实际 API 调整**）：

```rust
// 示意：识别一张 PNG
// 1) 选引擎：优先用户设置的语言（如 "zh-Hans-CN"），不支持就回退到用户系统语言
let lang = Language::CreateLanguage(&HSTRING::from("zh-Hans-CN"))?;
let engine = if OcrEngine::IsLanguageSupported(&lang)? {
    OcrEngine::TryCreateFromLanguage(&lang)?
} else {
    OcrEngine::TryCreateFromUserProfileLanguages()?
};
// 2) 解码图片为 SoftwareBitmap（BitmapDecoder + InMemoryRandomAccessStream），必要时缩放到 MaxImageDimension 以内
let bmp: SoftwareBitmap = decode_png_to_software_bitmap(&path)?;
// 3) 识别（在后台线程中阻塞等待异步结果）
let result = engine.RecognizeAsync(&bmp)?.get()?;
let text = postprocess(result.Text()?.to_string()); // 去 CJK 字符间多余空格等
```

**流程**

```
剪切板出现图片
   │  watcher：读位图 → 缩略图 → PNG 落盘 → 入库（ocr_status = pending）→ 通知前端 clip-added
   ▼
OCR 队列（串行、后台线程、低优先级）
   │  检查：用户是否开启自动 OCR / 图片尺寸范围 / 来源是否在黑名单
   │  选引擎：用户指定语言 → 回退系统语言 → 回退英文
   │  解码 → 必要时缩放 → RecognizeAsync（超时 15 秒，初始值）
   ▼
后处理：去 CJK 间多余空格、合并硬换行（保留段落）、统一全半角标点（可选）
   ▼
入库：ocr_text、ocr_lang、ocr_status = done / empty / failed，更新全文索引
   ▼
事件 ocr-done → 前端：列表项显示「已提取 N 字」、预览区展示结果
```

**后处理细则（初版，需实测迭代）**：
- 去掉相邻两个 CJK 字符之间的空格（据我了解 `Windows.Media.Ocr` 对中文可能按「词」插入空格，需实测确认）；中英文交界处保留空格。
- 以 `Lines` 为单位重建换行；相邻行若明显属于同一段（行尾无标点且下一行缩进相近）可合并，但此项容易出错，初版建议保持逐行输出并提供「合并为一行」按钮。
- 不做任何联网纠错。

**触发策略与设置**
- 默认开启「复制图片后自动识别」；设置中可改为「仅手动识别」（选中图片按 `Ctrl+O`）。
- 图片尺寸范围（初始值）：宽高均 ≥ 40 px，且不超过引擎最大边长（超过则缩放识别）。
- 识别语言：默认「自动（跟随系统语言列表）」；可手动选择简体中文 / 英文 / 繁体等已安装语言。
- **不自动改写剪切板**：识别完成后不会替换你的当前剪切板内容（否则会打断用户正在进行的粘贴）。如需「截图后文字直接进剪切板」，作为可选设置，默认关闭。

**界面行为（对应界面稿）**
- 状态：`识别中`（列表项细进度条 + 转圈）→ `已提取 N 字 · 语言`（绿色 OCR 徽标）/ `未识别到文字` / `识别失败，点击重试` / `缺少语言包，点击查看`。
- 预览区：上方为图片（识别区域用主题色描边高亮），中间语言与「重新识别」，下方为可编辑的识别文字，主按钮「复制文字」。
- 搜索：`ocr:关键词` 或直接搜索也会命中 OCR 文本（命中处高亮）。

**数据与存储**
- `clips` 增加 `ocr_text`、`ocr_lang`、`ocr_status`（`none / pending / done / empty / failed`）、`width`、`height`、`thumb_path`。
- 建议建立 FTS5 虚拟表 `clips_fts(content, ocr_text)`，用于搜索（需核对 SQLite 构建是否启用 FTS5；`rusqlite` 的 bundled 特性通常可启用，需核对）。
- 原图仅落盘（`%APPDATA%\Dogear\images\`），文件名用内容哈希。

**风险与降级策略**

| 情况 | 表现 | 降级与处理 |
|---|---|---|
| 系统没有对应 OCR 语言包 | 引擎创建失败或无法识别中文 | 检测 `AvailableRecognizerLanguages`；在预览区提示并给出「打开系统语言设置」入口（可尝试 `ms-settings:` 协议深链，需核对）；仍允许用英文引擎识别；记录 `failed` 原因 |
| Windows 版本不支持或接口不可用 | 调用报错 | 关闭 OCR 入口并说明原因，其他功能不受影响；评估启用备选引擎（可选下载） |
| 识别结果为空 | 图片无文字或清晰度不足 | 标记 `empty`，提示「未识别到文字」，保留「重新识别（放大 2 倍）」重试按钮（先放大再识别，需实测是否有帮助） |
| 图片过大 | 内存与耗时升高 | 先缩放到引擎最大边长以内；设置绝对上限（初始 8000 px，超出直接跳过并提示） |
| 识别很慢或卡住 | 队列堵塞 | 15 秒超时与取消；单线程串行；失败不影响列表使用 |
| 中文效果不理想 | 错字、字间空格 | 后处理；结果可编辑；记录样例并在 M0b 对比备选引擎，必要时提供「增强引擎」选项（P2） |
| 隐私 | 截图里含敏感信息 | 同黑名单规则；OCR 文本与原图同样可一键清除；不上传、不写日志 |
| 并发与功耗 | 连续多张截图 | 队列去重（相同哈希不重复识别）；笔记本电池模式下可设置为仅手动识别 |

**测试建议**：建立一个 `tests/ocr-samples/` 样例集（可含各类中英文截图），记录每次引擎或后处理改动后的人工打分，用于回归；不要把含隐私的真实截图提交到仓库。

`clips` 表（在 v1 基础上增加粗体字段）：

| 字段 | 类型 | 说明 |
|---|---|---|

| **thumb_path** | TEXT | 缩略图路径 |
| **width / height** | INTEGER | 图片尺寸 |
| **meta** | TEXT | JSON 字符串：识别的附加信息（颜色解析、JSON 行数深度、URL 域名等） |
| **ocr_text** | TEXT | OCR 结果 |
| **ocr_lang** | TEXT | 实际使用的识别语言 |
| **ocr_status** | TEXT | none / pending / done / empty / failed |

`settings` 表：键值对，新增 `smart_detect`（总开关与逐类开关）、`ocr_auto`、`ocr_lang`、`theme`（system / light / dark）、`reduce_transparency`、`paste_formatted_default` 等。

全文检索：`clips_fts`（FTS5，字段 `content`、`ocr_text`）。中文分词在 FTS5 默认分词器下效果有限（逐字或按字符分），初版可用 `LIKE` 兜底，必要时评估 trigram 分词器（需核对 SQLite 版本支持）。

去重规则：哈希已存在则只更新 `updated_at` 并排到最前；图片按像素数据哈希，OCR 结果复用，不重复识别。

| 名称 | 类型 | 说明 |

#### 11.5 关键流程

**记录流程**：系统通知剪切板变化 → 读取内容 → 判断不收录标记 / 黑名单 → 计算哈希 → 去重入库 → `detect` 识别类型（文本）或生成缩略图（图片）→ 图片入 OCR 队列 → 触发保留策略清理 → 事件通知前端。

**呼出并粘贴流程**：同 v1（记录前台窗口 → 显示并聚焦 → 选择 → 写回剪切板（标记为自己写入）→ 隐藏并恢复原窗口 → 发送 Ctrl+V → 失败则提示手动粘贴）。新增：写回的内容由 `variant` 决定（原文 / 格式化 / OCR 文字）。

#### 11.6 非功能性要求

- 性能：呼出到可输入小于 150ms（目标值，需实测），**动画不得阻塞聚焦输入**；1 万条记录下搜索无明显卡顿；识别耗时小于 5ms（目标值）。
- 资源：窗口隐藏时常驻内存尽量低；监听基于系统事件；OCR 仅在需要时运行。
- 隐私与安全：默认不联网；数据存本地用户目录；一键清空（含图片与 OCR 文本）；日志不记录剪切板内容。
- 稳定性：单实例；崩溃后重启不丢历史；关键错误写入本地日志。
- 可访问性：键盘全程可用；对比度满足 12.2 的要求；响应系统「减少动画」与高对比度设置。

### 12. 视觉与交互设计规范

> 设计目标：**简约大方、有苹果产品的质感**——大量留白、统一圆角、半透明材质、克制的配色、清晰的字号层级、细腻的动效；同时遵守 Windows 的使用习惯与系统字体，**不是在 Windows 上硬仿 macOS**。
> 以下数值为设计初值，来自界面稿（`prototype/index.html` 中的 CSS 变量），实现时以 `src/styles/tokens.css` 为唯一来源。

#### 12.1 设计原则

1. **留白优先**：信息分组靠间距和细分隔线，而不是边框与底色块。
2. **一个强调色**：全局只有一个强调色（靛蓝），其余为中性灰；类型色只用于小面积图标底。
3. **材质分层**：窗口为半透明材质，卡片为更实的半透明层，选中态为强调色浅底。
4. **克制的阴影与动效**：阴影柔和，动效短而轻，不炫技。
5. **键盘优先**：所有操作可键盘完成，底部始终提示常用快捷键。

#### 12.3 字体与字号层级

**字体栈（Windows）**

```
--font-ui: "Segoe UI Variable Text", "Segoe UI Variable", "Segoe UI",
           "Microsoft YaHei UI", "Microsoft YaHei", "Noto Sans CJK SC", sans-serif;
--font-mono: "Cascadia Code", "Cascadia Mono", Consolas, "Microsoft YaHei UI", monospace;
```

说明：
- 英文与数字：Win11 自带 Segoe UI Variable（可变字体，视觉接近 SF 的气质）；Win10 没有 Variable 版，自动回退到 Segoe UI，观感略有差别（可接受）。
- 中文：首选**微软雅黑 UI**（Windows 自带，无需打包）。思源黑体（Noto Sans CJK SC）仅作为回退或需要完全统一各机器观感时的可选项；它体积大（单字重通常数 MB 到十几 MB，需核对），不建议默认打包。
- **不使用、不打包 SF Pro**：Apple 字体的授权不允许在非 Apple 平台分发，所以「SF 风格」只体现在**层级与字重节奏**上，而不是字体文件。界面稿截图里的英文与数字因渲染环境没有 Segoe UI，由 Inter 等字体代替，**实际 Windows 上的字形会不同**。
- 等宽：Cascadia Code（Win11 自带，Win10 可能没有）→ Consolas。
- 字重：400 / 500 / 600（Segoe UI Variable 支持可变字重；YaHei UI 只有常规与粗体，500 会回落到常规，需实机查看层级是否仍清晰）。

#### 12.5 毛玻璃与 Win10 降级

**重要事实（需核对）**：
- WebView 里的 CSS `backdrop-filter` 只能模糊**网页内部**的内容，**无法模糊桌面或其他窗口**。要得到「窗口后面是模糊桌面」的材质，必须依靠系统级效果：设置窗口透明，并使用 Windows 的 Mica / Acrylic / Blur。
- Tauri 2 提供窗口特效配置（`windowEffects` 配置项 / `Window::set_effects` 一类接口，底层来自 window-vibrancy 一类能力），支持的效果与最低系统版本据我了解大致为：Blur（Win7 起）、Acrylic（Win10 1809 起，但在部分版本拖动与缩放时有性能问题）、Mica 与 Tabbed（Win11，其中 Tabbed 需较新的 Win11 版本）。**以上均需对照 Tauri 与 window-vibrancy 官方文档核对，并在目标机器实测。**
- 对于「呼出即用的临时面板」，我推荐 **Acrylic（Win11）** 做材质，因为它能透出背后窗口的模糊；Mica 更适合长期存在的主窗口，且主要取壁纸色。最终以实测观感为准。

**降级阶梯（`effects.rs` 实现，按顺序尝试）**

| 级别 | 条件 | 表现 |
|---|---|---|
| 1 | Win11 且特效可用且系统「透明效果」开启 | Acrylic（或实测更好的 Mica）+ 半透明 `--panel` |
| 2 | Win10 1809 以上，Acrylic 实测流畅 | Acrylic；若拖动卡顿，改用 Blur |
| 3 | 特效应用失败，或系统关闭透明效果，或节能模式 | 半透明纯色：`--panel` 的不透明度提高到约 0.94，无模糊 |
| 4 | 系统高对比度模式，或用户在设置中开启「减少透明效果」 | 纯色 `--panel-solid`，使用系统高对比度色（`forced-colors` 媒体查询） |

实现要点：
- 前端通过 `get_effect_state()` 在 `<html>` 上设置 `data-effect="acrylic|blur|solid"`，由 CSS 变量切换 `--panel` 的不透明度与是否使用 `backdrop-filter`（卡片内部的 `backdrop-filter` 只在需要时使用，避免叠加性能开销）。
- 原型中的毛玻璃是用网页背景 + `backdrop-filter` **模拟**的，**真实效果取决于系统特效，两者观感不会完全相同**。
- 不要在列表里的每一行都使用 `backdrop-filter`。

#### 12.6 图标风格

- **界面图标**：24px 栅格、1.8px 描边、圆角端点与圆角拐角（SF Symbols 的气质）；类型图标放在 38px 圆角方块里，底色为类型色的 14% 透明度，线条为类型色。界面稿里的图标为自绘 SVG 精灵；正式开发建议使用宽松许可的图标库（如 Lucide，需核对许可与图标是否齐全）以降低维护成本。
- **应用图标**：squircle 底板 + 柔和渐变 + 折角纸张，见 8.4。
- **托盘图标**：单色，轮廓优先，16 / 20 / 24 / 32px 均需检查；随系统深浅色切换黑 / 白版本。
- **收藏标识**：小号图钉或星标，使用 `--warn`；P2 可加入「折角」彩蛋（收藏项右上角出现小折角）。

#### 12.7 动效

**原则**：只用 `transform` 与 `opacity` 做动画；短、轻、可打断；尊重系统「显示动画」与 `prefers-reduced-motion`（WebView2 是否映射系统「动画效果」设置需核对）。

| 场景 | 时长 | 曲线 | 描述 |
|---|---|---|---|
| 面板呼出 | 180ms | `cubic-bezier(.2,.8,.2,1)` | 透明度 0→1，缩放 0.98→1，向上位移 6px→0；**聚焦输入不等待动画结束** |
| 面板隐藏 | 120ms | `cubic-bezier(.4,0,1,1)` | 透明度 1→0，缩放 1→0.99；隐藏后再真正 hide 窗口 |
| 选中项移动 | 160ms | `cubic-bezier(.2,.8,.2,1)` | 选中高亮条随上下键平滑滑动（共享元素） |
| 悬停 / 按下 | 120ms | `ease-out` | 背景色变化；按钮按下缩放 0.98 |
| 新记录进入 | 220ms | `cubic-bezier(.2,.8,.2,1)` | 顶部插入，其余项下移，新项淡入 |
| 预览切换 | 140ms | `ease-out` | 右侧内容淡入 + 4px 位移；快速连按上下键时可跳过动画 |
| 分段控件切换 | 200ms | `cubic-bezier(.2,.8,.2,1)` | 白色滑块平滑移动 |
| OCR 状态 | 转圈 1s 线性循环；完成时 200ms 淡入文字 | 线性 / `ease-out` | 进度条使用不定进度的流光，完成后变为「已提取 N 字」 |
| 主题切换 | 200ms | `ease-out` | 颜色过渡 |

降级：开启「减少动画」时，所有位移与缩放动画取消，仅保留 80ms 以内的透明度过渡。
